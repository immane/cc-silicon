# T02: Control, Scheduling, and Diagnostic Chips

Prerequisite T01/C01–C06. Directory `chips/control/`. Permission upper bound: read `config/control/tasks`; read/append `sources` (CT02 source import only) and `diagnostics` (CT11 only); read `artifacts` (CT14 output fragments only, read-only); write its own control records and proposals. This envelope is only the package-level upper bound (T01 §5): each chip must still refine it to its exact field-scoped manifest before implementation, and stores/queues/results may only be modified by the designated commit path (no chip mutates them directly; the application backend applies CT06's validated commit decision, including CT02's source-import and CT11's diagnostic appends). The chips below are all CPU reference, propagation; called by the motherboard, workers must not call them.

Fixed topology: TaskSelect → TaskGuard → the corresponding worker sub-pipeline → ProposalValidate → TaskCommit → ResultResume/PhaseAdvance. Route by task rather than traversing the entire catalog every tick. PhaseAdvance only looks at completion facts and never performs compilation on its behalf.

Runtime/layer realization (selected draft direction, 2026-10-04; doc-level only, **not an accepted contract and not owner/integrator-approved** — no chips are implemented; registered in [M1_PART_A_CONTRACT_PROPOSAL.md](M1_PART_A_CONTRACT_PROPOSAL.md)). The semantic topology above is unchanged:

- **CT03 TaskSelectChip is decision-only.** It is a `RestrictedChip` invoked exactly once through its installed `ProjectedChip`/`ChipAdapter`; the adapter writes the canonical `SelectionBatch { entries: Vec<SelectionEntry> }` (`SelectionEntry { task, chip, layer, dispatch_ordinal }`) to the selection wire. The **application dispatcher** applies the batch (marks each task `Running`, records `control.selected`/`tasks.active` as the quota-1 projection, records `tasks.in_flight` and `control.dispatch_cursor`, removes it from its canonical `stage_queues[stage]`). No chip mutates selection state directly, and there is no duplicate selection. `wires.selected` is only the optional quota-1 compatibility projection; the canonical report field is the ordered `dispatched` set.
- **CT05 ProposalValidateChip is validation-only** (decision proposal; no store mutation).
- **CT06 TaskCommitChip may propose the validated commit, but commits nothing itself.** The commit path / application `CompilerBackend` performs the mutations via `commit_proposals` (validate → capacity preflight → infallible apply). New tasks become visible next tick.
- **Layers/runtime.** Dedicated fixed control layers (`SELECT_LAYER < GUARD_LAYER < WORKER_BASE`), with one routed chip per worker layer. The `CompilerDriver` owns a private `Motherboard`; its custom `Backend::execute_layers` ticks CT03's `ProjectedChip` exactly once, the dispatcher applies the ordered batch, then it invokes CT04/guard and exactly the routed worker layer per dispatched task (with `dispatch_cursor`), collects the wire proposals, calls `commit_proposals`, and records the canonical `bus.report`. `TickReport`/`TickOutcome`/`Resolution` and the `fail_selected` error path are **proposed** to move to a new `report.rs`/`driver.rs`; **no `report.rs` exists in the crate today**. The root `Motherboard` still owns `reset_wires`, `latch`, and `advance_tick`; no root-framework change is required.
- **Queues/results/arenas** are written only by the commit path/integration, never by a chip body.

Batch/pipeline realization (user in-principle direction, 2026-10-04 — a rev-21 `/6` working basis, **not** a freeze/chip authorization; see [ADR-0002](../architecture/ADR-0002-DETERMINISTIC-COMPILER-PIPELINES.md) and [M1 Part A](M1_PART_A_CONTRACT_PROPOSAL.md) §10.5). The semantic topology above is unchanged, but it is realized over a **bounded, ordered `SelectionBatch`**:

- **CT03 is decision-only and batch-bounded.** It selects at most `max_inflight_per_tick` eligible tasks (one ordered batch, up to one entry per eligible stage), never mutates `control`/`tasks`, and there is still exactly one selection path. The dispatcher applies the whole batch in deterministic `(stage ordinal, phase priority, enqueue ordinal, TaskId)` order, marking each task `Running` and recording it in the in-flight set. The batch is preflighted (`SelectionBatchOverflow`, `DuplicateSelection`) before any dispatch.
- **CT04 guards per dispatch.** It checks owner/kind/preconditions/version for each dispatched task; the backend ticks the guard layer and **only** that task's routed worker layer, one task at a time (`dispatch_cursor` = the task's position in the in-flight set).
- **CT05 validates the whole ordered batch**, including batch-scoped cross-task checks; it is validation-only and mutates no store. The same-tick write-conflict predicate is `(StoreId, field, record)`: a declared append-only field is permitted only when the appends are semantically independent under a hashed rule, otherwise the whole batch is rejected (`CrossTaskWriteConflict`); patches to the same record always conflict. **Rev 21 scope (user, in principle):** each field has exactly **one** owner, so this predicate covers two tasks of the *same* owner group appending one append-only field or two patches; it is **not** a shared-writer carveout and never permits a second owner group (`StoreOwnerViolation`). `sources.spans` is **T03-only** (T04/T05 write no spans). The batch-conflict audit owner is a **proposed** VF04 extension; that extension is **not defined today**, so it is a residual, not a defined verifier (not VF12).
- **CT06 proposes the whole commit** in the extended deterministic order `(dispatch_ordinal, enqueue_ordinal, TaskId, proposal index)`, bounded by `max_proposals_per_tick` (`proposals.len() + total_drafts`). The commit path/backend performs **one ordered atomic commit** per tick; a failed batch commits nothing. **Rev 25 F2:** the frozen `/5` `routing.rs` `fail_selected` single-task obligation (that task becomes `Failed` with a diagnostic when capacity allows) is **preserved**; the batch claim "fails every dispatched task exactly once so no `Running` survives" was the **intended generalization, BLOCKED (H6)** — clearing the in-flight set does not clear `TaskState`/`Running` (see below and the M1 proposal §7/§10.5). **Rev 27 (user direction in principle, 2026-10-04; H6):** the batch-failure **recovery direction** was **selected in principle** — on a failed atomic semantic batch commit, **every** dispatched task, in **dispatch order**, transitions **exactly once** to `TaskState::Failed`, attaching a committed `DiagnosticId` when diagnostic/record capacity allows and otherwise the `TaskState::Failed(DiagnosticId::NONE)` sentinel, so **every** dispatched task leaves `Running`; **clearing the in-flight set is not itself a transition** (and does not clear `TaskState`/`Running`). This **generalizes** the verified `/5` single-task sentinel semantics (unchanged). **Rev 30 (user authority decision, 2026-10-05; H6 scope + mechanism selected; CDR rev 42):** the user **rejected the deferral** of the H6 mechanism to a later CDR and **selected an explicit quota>1-capable bounded recovery mechanism to be frozen in `/6`** — **pre-dispatch errors before any state mutation leave the affected tasks `Ready`**; a **semantic batch commit failure commits no semantic state**; then a **deterministic bounded recovery mutation processes the dispatched tasks once in dispatch order to `Failed`**; **no pre-reservation of N diagnostics**; a **per-task diagnostic attempt** falls back to `DiagnosticId::NONE` when capacity is insufficient; and a **state guard prevents the duplicate transition**. This is a **selected mechanism to be frozen in `/6`**, no longer merely a direction. **Still `[INT]`/co-freeze/pending:** the **exact atomic-commit realization requires T01 integrator approval**, and the H9 numeric inventories (dispatcher mutation boundary, residual-inflight exhaustive paths, limits/stages/hash/error codes) and the T02/T13 owner fixtures/sign-offs remain **pending**; the mechanism is **not implemented or frozen**. New tasks become visible next tick.
- **CT07 joins across in-flight/children over committed IDs or own-task-batch keys.** A parent resumes only when all its committed child results are present; `Proposal::AwaitChildren` (with `ChildRef::Committed`/`ChildRef::OwnBatch`, same-task only) sets `TaskState::Waiting(WaitSet { children, host_request: None })` (the **only** awaited-child source; no `continuation.awaited`). **CT07 is decision-only; the commit-apply phase performs the transition and reinserts the resumed parent into its own `stage_queues[stage_of(parent.kind)]` (the parent task's kind — H2; the realization handles an absent `continuation`), so it is selectable next tick.** All committed children `Completed` → parent `Ready`; any committed child `Failed` → parent `Failed` exactly once, **never** `Ready` (H4). Cursors/joins never point at another task's draft, a wire, or an address; `ContinuationRef::OwnBatch` resolves within the same task's batch at commit. **Rev 26 (user decisions A/B, in principle, 2026-10-04; T02-owner + T01 acceptance pending):** the own-task-batch `OwnBatch`/`ChildRef::OwnBatch` keys are a **transient wire/proposal input only**, validated and resolved to committed IDs **before persistent state**, so no durable cursor/`WaitSet`/join points at a draft/wire/address — the user's **narrow interpretation** of [Guardrails](COMPILER_DEVELOPMENT_GUARDRAILS.md) §6.1 (guardrail text **unamended**; **T01 implementation-confirmation pending**). `WaitSet` is the **sole** awaited-child-ID source and `ContinuationRecord` carries no duplicate `awaited`; the **T01 §4 supersession is a formal `/6` amendment only (no `/5` edit)**, with **T01 + T05 acceptance pending**. **Rev 30 (user authority decision, 2026-10-05; CDR rev 42, T02/T05 roles):** the CT07 carrier question is **settled — the join is a commit-apply invariant with no new CT07 committed carrier/family** (CT07 computes the join decision but commits nothing), and the sibling-policy question is **settled — await-all**, i.e. **all committed children terminal before the parent decision** (any committed child `Failed` fails the parent once and never sets `Ready`). These two subdecisions are accepted; the rev-30 sync does **not** freeze CT07 and the remaining open items stay open (below). **Rev 34 (OPEN-02 result delivery; T01/T05/T02 `/6` co-freeze):** the join consumes no child result; child results stay committed/unconsumed and consumption stays with the parent's own next-tick atomic commit (or transfers at join into parent-owned durable state), with the required `join_then_replay_retry` fixture; the exact carrier/envelope stays open. Still not a freeze.
- **CT09 advances the phase only when all canonical `stage_queues` are empty/waiting** (no ready or waiting task remains across all stages); `tasks.ready` is a derived view, not the authority.
- **CT10 checks progress/budget over the batch** (no wall-clock); a `Progress` reschedules to next tick within `max_task_progress` and reinserts into the task's **own canonical `stage_queues[stage]`** (never the derived `tasks.ready`).
- **CT13 cancel handles an in-flight set**, not a single active task, and remains idempotent; cancel is evaluated once per tick before selection.

`max_inflight_per_tick` defaults to **1**; the quota = 1 path is the baseline equivalence mode and must equal the single-active-task design under the **canonical semantic comparison projection** (semantic records/results/diagnostics + semantic trace excluding scheduler-only registers), with the new scheduler snapshot separately deterministic/replay-identical. It is **not** byte-identical snapshots and **not** a frozen single-active-task architecture. A quota `> 1` is a measured, post-`/6`, integrator-accepted change; no throughput claim is made here. The batch semantics are inert until the pipeline `/6` freeze.

These are contract-realization decisions, not implemented behavior.

### T01 architecture-critical items — alternatives and required properties (T02 does NOT choose)

The four items below are **T01 selections**; T02 lists viable alternatives and the properties any choice must satisfy, and records **no** chosen boundary.

1. **Dispatcher `Ready→Running` mutation vs the one ordered atomic commit boundary.** *Viable alternatives:* (a) the dispatcher's per-batch `Ready→Running` + in-flight population is a **distinct pre-worker mutation** outside the semantic commit; (b) it is folded into the single ordered atomic commit. *Required properties for either:* the transition is **one-per-dispatch**, deterministic (dispatch order), replay-visible in the scheduler snapshot, and does not make semantic store state observable before commit; exactly one writer is named.
2. **`in_flight` clear ownership/order relative to the bounded H6 recovery.** *Viable alternatives:* clear at latch after recovery; clear inside recovery as the final step. **Rejected as incompatible (rev 33):** "clear as a separate post-recovery tick-start reset" — a next-tick-start clear necessarily leaves a residual in-flight entry across the latch boundary, directly contradicting the required property below (and item 4). *Required properties:* the clear is **not itself a transition**, does not clear `TaskState`/`Running`, happens at the **current latch only after** every dispatched task has a terminal/`Waiting`/`Progress` outcome or the H6 recovery, and leaves **no** residual in-flight entry **at that latch**. **The exact clear owner and order remain a critical T01 decision**; T02 selects none. *Testable invariant:* a tick fixture over every path (success, semantic batch failure, pre-dispatch error, empty proposal vector) asserts `tasks.in_flight` is empty **at latch** and that no in-flight entry is observable at the next tick start.
3. **Failure recovery mutation primitive.** *Viable alternatives:* (a) the rev-30 selected **no-pre-reservation per-task-attempt** bounded recovery; (b) a T01-approved atomic terminal path reserving bounded terminal diagnostic slots before dispatch (retained implementation option, **not** selected). *Required properties:* bounded (no unbounded scan), dispatch-ordered, exactly-once, diagnostic-capacity-explicit with `DiagnosticId::NONE` fallback, state-guarded.
4. **No-residual / no-`Running` guarantee.** *Required properties (T02 does not claim a proof):* for **all** tick paths — success, semantic batch failure, pre-dispatch error, **empty proposal vector**, **cancel tick**, **tick-budget tick**, **join-only tick**, and **`Progress`-only tick** — no dispatched task remains `Running` at latch and no residual in-flight entry survives; the guarantee is **conditional on the H6 recovery realization** and would be verified, not asserted. *Verifiable requirement (rev 33; corrected rev 35):* for each path the latch post-condition is asserted **at latch, before `reset_wires`**:
   - **dispatched tasks:** every dispatched task has exactly one outcome with `state(t) ∈ {Completed, Failed, Waiting, Ready}`; a `Ready` reached by a `Progress` outcome has `ready_tick = tick+1` and exactly one own-stage queue entry (H6-M16); the empty-proposal outcome rule is the still-open explicit rule (H6.5), so the task is never silently `Completed` and never `Running`;
   - **pre-dispatch error:** the affected (selected, not dispatched) task(s) remain `Ready` with `state`/`ready_tick` unchanged — no dispatch, no transition, no diagnostic consumed (H6.1/H6-M03);
   - **cancel tick / tick-budget tick:** no new selection, dispatch, or commit; the ready/waiting task disposition (cancel) and the cancel-vs-tick-budget precedence are the contract's chosen/frozen rules — **unresolved (T01/[INT])** — with repeated cancel idempotent and exactly one terminal report record (H6-M13/M14);
   - **join-only tick:** a `Waiting` parent is in no stage queue; when all committed children are terminal it resumes **exactly once** — all `Completed` → `Ready` + one own-stage insertion, any `Failed` → `Failed` once, never `Ready` (H6-M15);
   - **`tasks.in_flight = ∅`** at latch, with a cross-tick assertion confirming the set is still empty at the next tick start (i.e. the tick-start state was not the mechanism that cleared it).
   T13 H6-M01/M02 (latch conjunction), H6-M10 (wire lifetime), H6-M12 (quota-1 projection vs scheduler snapshot); the H6.5 empty-vector rule stays open (OB-2) and the M13/M14 disposition/precedence rules stay unresolved (OB-3).
