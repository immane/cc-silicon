# T06: Scope, Symbol, and Type Chips

Prerequisite T01. Directories `chips/symbols/`, `chips/types/`. Read symbols/types/config and task inputs; write this owner's records/proposals. Symbol addition/deletion can only be done by the designated declaration/scope tasks; type interning is not permitted to parse the AST incidentally. parse/sem is served through task requests and must not call the chip methods below.

Type records cover the types required by the corpus, such as scalar, pointer, array (complete/incomplete/VLA), function (prototype/old-style/variadic), struct/union, enum, qualified/atomic, GNU vector/complex, etc. target-dependent layout is not privately computed here; it is handed to T08.

> **6a. Records and field shapes (exact, as currently proposed; not frozen).** These are the field sets the M1 T06 slice is expected to materialize; every field is grounded in the proposal and none is invented here.
>
> - `ScopeRecord { parent: Option<ScopeId>, kind: ScopeKind }`, with `ScopeKind` an **M1 closed set `{ File, Block }`** (function/prototype/member/tag/label-as-scope are explicit **M1 deferrals**; `(void)` opens no prototype scope). Draft form: `ScopeDraft { parent: Option<RecordLink<Scope>>, kind }` (**no** chip ordinal).
> - `ScopeEventRecord { scope: ScopeId, kind: ScopeEventKind, at: NodeId }`, `ScopeEventKind { Enter, Exit }`; append-only, **order = `ScopeEventId`** (no stored ordinal). Draft form: `ScopeEventDraft { scope: RecordLink<Scope>, kind, at: RecordLink<Node> }`.
> - `SymbolRecord { name: NameId, scope: ScopeId, kind: SymbolKind, ty: Option<TypeId>, linkage: Linkage, storage: StorageDuration, decl: NodeId }` (`ty: None` only for `Label`); `SymbolKind { Object, Function, Typedef, EnumConst, Label, StructTag, UnionTag, EnumTag }`; `Linkage { None, Internal, External }`; `StorageDuration { None, Static, Automatic, Thread, Allocated }`. **No `namespace` field** (derived from `kind`, item 3). Draft form: `SymbolDraft { name: RecordLink<Name>, scope: RecordLink<Scope>, kind, ty: Option<RecordLink<Type>>, linkage, storage, decl: RecordLink<Node> }`.
> - `TypeRecord { kind: TypeKind }` (**no `canonical_key`**); `TypeKind { Void, Bool, Char(CharKind), Int { rank, signed }, Function { result: TypeId, params: Vec<TypeId>, prototype: bool, variadic: bool } }`, `CharKind { Plain, Signed, Unsigned }`, `IntRank { Short, Int, Long, LongLong }`. Draft form `TypeDraft { kind: TypeKindDraft }` (no `IntRank` char rank; `Function` params are `RecordLink<Type>`).
> - **Symbolic `int` and `int(void)`:** the M1 `int` is `TypeKind::Int { rank: Int, signed: true }` and the `main` type is `TypeKind::Function { result: <int>, params: [], prototype: true, variadic: false }` — both **symbolic, with no target width/bit width** (width/bit-pattern remains Part B/probe-gated). No numeric enum discriminants are asserted.

> **6b. Scope-enter / `main` declaration / identifier-leaf `decl` identity and declarator-completion visibility (candidate direction; not frozen).**
>
> - **File scope-enter** is the item-2 accepted stage edge: after the committed `TranslationUnit` node, a T06 task emits exactly one file-scope `Enter` with `ScopeEventKind::Enter`, `scope` = the file `ScopeRecord`, and `at` = the **committed TU `NodeId`**. The file scope has **no `Exit`** in M1 (never closed).
> - **Declaring `main`** is a `SymbolRecord` in the **file** scope (no distinct M1 function scope): `kind: Function`, `ty` = the `int(void)` function `TypeId`, `decl` = the `Identifier`-leaf node naming `main`. Function/parameter scoping for `main` is carried by the block scope plus `SymbolRecord.decl`.
> - **`decl` is the `Identifier` `NodeKind` leaf** that names the symbol (not a `Declarator`/`Declaration`/`FunctionDefinition` wrapper); it remains the **symbol-identity and diagnostic location**. **Semantic visibility is a separate boundary:** per C11 6.2.1p7 the scope of an ordinary identifier begins **just after the completion of its declarator**, so the lookup point-of-declaration tuple `(source: SourceId, start: u64, end: u64, decl: NodeId)` derives `start`/`end` from the **completion point of the complete declarator** — the span of the declarator's `last_token`, reached from the committed `decl` leaf through the committed AST parent links (the exact T05 `NodeKind`/ownership/token-range semantics remain the T05 `/6` item): `declarator NodeRecord.last_token -> committed TokenRecord.span -> SpanRecord.source/start/end` (nodes have **no `span` field**) — **not** from the declarator's full range (a full range would expose the symbol inside its own declarator) and **not** from the identifier leaf. The tuple's fourth component stays the leaf `decl: NodeId` so identity is stable.
> - **Visibility contrast (required test; C11 6.2.1p7):** with `int n = 3; void f(void) { int n[n]; }` the array bound is inside the inner declarator, so the inner `n` is not yet visible there and the bound must resolve to the **outer** `n`; with `void f(void) { int n = n; }` the initializer follows the completed declarator, so its `n` resolves to the **declared inner** `n` (self-initialization; the indeterminate value is a separate concern). Both spellings place the identifier leaf before the second `n`, so a leaf-position rule cannot distinguish them.
> - **Block scope-enter/exit:** both `Enter` and `Exit` reference the **`Block` node** (distinguished by `kind`); the Block node's token range supplies the boundary (`first_token` = `{`, `last_token` = matching `}`), so `at` is a real node with no fabricated boundary node.
> - **Scope-exit lifecycle (candidate validation direction, §7 phase 2b, no mutation; DOC-13 correction):** over **committed + same-batch resolved** events, exactly **one `Enter`** per `ScopeRecord` and **at most one `Exit`**, with `Exit` **strictly after `Enter` in `ScopeEventId` order**; every `event.at` resolves to a live committed `Node` (or a same-batch `NodeDraft` resolved in the batch); a second `Enter`/`Exit`, an `Exit`-before-`Enter`, a dangling `at`, a new `ScopeDraft` with no `Enter`, a **duplicate scope-owner creation**, or a file-`Exit` policy violation is `ScopeLifecycleViolation` (**pre-mutation**). A scope is identified by its **owner lexical node** — the resolved `at` of its single `Enter` (the committed TU `NodeId` for the file scope; the `Block` node for a block scope) — **not** by `(parent, kind)`, so sibling blocks/functions sharing `(parent, kind)` are **legal distinct scopes**; the only duplicate-creation rejection is a new `ScopeDraft` whose resolved owner `at` node is already claimed by another `ScopeRecord` (committed or same-batch); the claim is keyed on the owner node, so `(parent, kind)` is never the duplicate key. The check never keys on a **live** arena record: a closed scope **retains its record** (TY02), so close must not block later siblings and the owner claim is permanent. The **M1 single-function fixture cardinality** (one `main` ⇒ one file scope + one block scope) is a **fixture property**, not a structural rejection of further block scopes. Scan is one pass over a `BTreeMap<ScopeId, …>` (never a hash map).
>
> **6c. Deterministic lookup (candidate direction; item 3 delegated, not signoff).** TY03 walks the **active scope chain only** (`scope` upward to the file scope; never a closed/sibling scope); given a name and query point `(source, qstart, qend, qNode)` it returns the ordinary-namespace symbol whose point-of-declaration tuple — `(source, start, end, decl)` with the **complete-declarator** completion `start`/`end` and the `Identifier`-leaf `decl` (§6b) — is `<=` the query tuple under the total order `(source, start, end, NodeId)` and is the **greatest** such; a same-scope tie selects the **higher `SymbolId`**, otherwise the **innermost active scope** wins; no candidate ⇒ missing (`NoSuchSymbol`). A lookup whose qualified name resolves in a **different** namespace is a **miss, not a conflict**. M1 has **no general type-compatibility model** (`TY21`/`TY22` deferred): the only commit-path structural rejection is an exact duplicate `(name, scope, kind)` append (`SymbolConflict`); `RedeclarationConflict` is a **chip diagnostic**, never a `CommitError`.

Commit runs **no structural dedup** and reuses the producer's committed id. > **7. Exactly-once File Enter claim via `ResultRecord.consumed` — integration-selected delegated candidate clarification (M1 T06; 2026-10-05; NOT an `[OWNER:T06]`/`[OWNER:T05]` signoff, NOT T01 `[INT]` acceptance, and NOT frozen).** Under the same explicit 2026-10-05 user delegation used for item 3, and grounded in the frozen `/5` code (`ResultRecord { task, kind, value, version, consumed: bool }` and the exactly-once `consume_result` claim API) plus the item-5 / T05-item-F TU carrier, the M1 integration agent clarifies **how** the item-5/6b file-scope `Enter` is made exactly-once. It **amends neither** the prior accepted stage-edge direction (item 2) **nor** the item-5 carrier, and it **preserves** all other T06 defaults.
>
> **7a. What is and is not enough.** `TaskState::Completed(ResultId)` **plus** the generic `ResultValue::Record(RecordRef::Node(root_node_id))` payload **identifies** the TU root (`root_node_id`), but by itself **does not** make File `Enter` exactly-once: completion is a durable fact, yet without a durable claim a later tick could re-observe the committed result and enqueue a **second** `Enter` (and the committed `ResultRecord` stays observable for its whole lifetime). The duplicate-suppression mechanism the item 5/6f co-freeze list leaves open is therefore resolved **candidate-ly** as follows.
>
> **7b. Durable claim = the existing `ResultRecord.consumed`.** The candidate uses the **existing** `ResultRecord.consumed: bool` flag on the committed TU result as the **durable claim**; **no new** `ResultValue` variant/family, `RecordRef` tag, record, arena, hash, or numeric code is introduced, and the claim is **not** held in a transient wire/latch. The claim is **consumed atomically with the enqueue of exactly one scope-enter task** (`symbol_type.scope-enter`, item 2), reading `root_node_id` from the same committed result payload.
>
> **7c. Commit trigger (exact).** The claim + enqueue happen **only after the result/node are commit-visible**: `TaskState::Completed(ResultId)` is committed and the referenced committed `NodeId` (`root_node_id`) exists committed (via the item-5 generic `Record` payload). They run in the **single commit-apply mutation site and same tick** — claim and enqueue are one atomic unit (`consumed=false -> true` exactly once), so a crash/partial application cannot leave a claimed-but-unenqueued or enqueued-but-unclaimed state. **Fallback if atomicity is unavailable:** if the `/6` frozen commit machinery cannot combine the claim and the enqueue into one commit-visible unit, **T01 must define an equivalent persistent delivery claim** (T05 item F point 5); this candidate does not invent or freeze that mechanism.
>
> **7d. Consumption semantics, retry, and liveness.** Exactly-once relies on the existing invariant that a consumed result is **never re-consumed** (`consume_result` returns `ResultAlreadyConsumed`), so re-observation cannot enqueue a second `Enter`. **Caveat / open point:** frozen `/5` `consume_result` returns a **clone of the whole `ResultValue`** and offers **no partial/destructive claim API**; `consumed` also already governs **general T01 result hand-off**. The candidate therefore requires either (i) a T01-provided claim consumed **only** by this edge, or (ii) **proven** non-overlap with other consumers of that result — both remain co-freeze. **Retry/liveness:** if the committed TU result exists but the file-scope `Enter` was not produced/in flight, the edge **re-claims nothing** and the T06 task is re-driven via the **existing** task/await mechanism; normal completion, explicit `Wait`, or typed `Fail` must hold. Whether a consumed-but-unprocessed claim needs a **separate T01-liveness provision** is an open co-freeze item; no second/amended claim may be emitted.
>
> **7e. If the envelope differs.** If T05/T01 later freezes a **different** TU result/envelope (item 5 permits this), an **equivalent durable persistent claim** is still required; the claim must **not** be moved to a transient latch/wire. The `ResultValue::{Records,DraftRecords,Empty,Ack,Diagnostic}` variants carry **no exactly-once claim**, so they alone cannot substitute.
>
> **7f. Co-freeze, not signoff.** The **exact claim trigger, consumption semantics, retry/liveness provision, and the File-`Enter` enqueue-payload manifest** (the precise field-level payload of the scope-enter enqueue) are **T01/T05/T06 `/6` co-freeze**, not fixed here; CDR row **E remains PENDING**. Item 7 is a **delegated candidate clarification only** — not an `[OWNER:T06]`/`[OWNER:T05]` signoff, not T01 `[INT]` acceptance, and not frozen.
>
> **8. OPEN-01 TU-root/scope startup-order candidate — early TU-root commit order (delegated candidate default under explicit user delegation, 2026-10-05; NOT an `[OWNER:T06]`/`[OWNER:T05]` signoff, NOT T01 `[INT]` acceptance, and NOT frozen).** For the documentation-review OPEN-01 ring, the candidate M1 order commits the TU **root** early in the registered `parse.TranslationUnit` task's first commit-visible batch (after the full token stream incl. EOF is committed) and fires the accepted item-2 `parse.TranslationUnit -> symbol_type.scope-enter` edge on that **committed root** while the parse task is `Waiting` (stage-order guard: a ready `parse` task would otherwise precede the `symbol_type` task); the T06 scope-enter task then creates the file `ScopeRecord` and its single `Enter` (`at` = the committed root `NodeId`, no Exit), and the parse resumes with the committed file `ScopeId`. This **qualifies the item-5 "after task completion" trigger and the item-7 `ResultRecord.consumed` claim for the File-Enter edge only**: the trigger is the committed root append, and exactly-once is structural (one root append per TU), so neither the `consumed` claim nor its atomic-claim fallback is required for this edge (both remain candidates for completion-triggered/other result hand-offs; OB-11/OB-50 stay open). Item-2's accepted direction and item-5's terminal carrier (points 1–2) are preserved. **Fallback if rejected:** the explicit M1 no-scope parse path + the `M1-START-01` no-prebuilt-scope startup fixture (proposal §24.14). **Still open (T05/T06/T01 `/6` co-freeze):** the edge-enqueue realization (same-batch link vs T01 commit-apply hook) and payload encoding, duplicate-root validation, the root-range/descendant invariant, and the bootstrap task kind/stage. CDR row **E stays PENDING**.

Key points: TY21's recursive type graph needs a visited pair to avoid cycles; it is not a recursive chip call. TY13's target parameter comes from T01 and must not hardcode the host width. Conversion results must contain actual cast nodes/plans and must not merely change the type in a way that makes the IR lose sign/zero extend. **M1 Part A qualifier:** for the M1 Part A slice, TY13's canonical `int` and the exercised TY25/TY26/TY27 `int→int` cases are **symbolic identity** — they read no target width/bit-pattern and use no target bitvector; the legacy `target` input above and the target-bitvector positive/negative cases apply only to probe-gated Part B / non-M1 conversions.

Additional acceptance: each conversion constructs positive and negative cases with the target bitvector; type and lookup results are fully serializable; during parse, the order of TY01/07/08/03 is made explicit by an integration fixture. GNU vector/typeof type services, once built by T12, still reuse the compatibility protocol here. **M1 Part A qualifier:** the target-bitvector acceptance above is Part B/probe-gated; the M1 Part A `int`/`int` conversions assert only the symbolic result and no target bitvector.
