# T04: Final C Token and Literal Chips

Prerequisite T01; input is PP04/final expanded tokens; directory `chips/lex/`. Read pp tokens, config target/dialect, source locations; write lex tokens/literal records and proposals. Preprocessing numeric values must not be treated directly as valid C constants.

Protocol `LexRequest(pp_token_id/range, mode)` → `TokenResult`; numeric parsing uses child tasks; multiple tokens may be merged into a string. Decoded results for integers and FP retain the source spelling, format, and bit pattern for subsequent diagnostics/IR.

| ID / Chip | Input → Output | Function and Goal | Specified Acceptance |
|---|---|---|---|
| LX01 TokenClassifyChip | PpToken → LexTask | Dispatch identifier/number/literal/punctuation; EOF is unique | Unknown character, bad pp-number, empty input |
| LX02 IdentifierDecodeChip | IdentifierSpelling → NameId | UCN/encoding/dialect character rules; stable intern | Valid Unicode, illegal escape, ID for identical spelling |
| LX03 KeywordClassifyChip | Name/mode → KeywordOrName | Standard and GNU keywords/aliases per dialect | typedef names are not forcibly converted to keywords in the lexer |
| LX04 PunctuatorDecodeChip | Punctuator → TokenKind | All C operators, digraph mapping, ellipsis | `<:`, `%:`, `...` and `.` |
| LX05 IntegerRadixChip | NumberSpelling → DigitSequence/base | Decimal/octal/hexadecimal and binary where the corpus requires it; validate digits | `09`, 0, empty 0x, huge constant |
| LX06 IntegerSuffixChip | NumberTail → Suffix | U/L/LL order, case, extended suffixes controlled by mode | `ULL`, `LLU`, repeated U, mixed case ll |
| LX07 IntegerValueChip | Digits/base → UnsizedBits | Big-integer decoding with no host overflow and range diagnostics | Beyond u64, int128 candidate, leading zeros |
| LX08 IntegerTypeSelectChip | Bits/base/suffix/target → TypedLiteral | C candidate lists: decimal and non-decimal differ. The committed candidate type is carried on the T04-owned `LiteralRecord.candidate_type` (see §"Committed literal record" below); `Lx08CandidateType` is **symbolic/target-independent** with M1 literals `2` and `3` typed `Int` and **no bit width** | 2147483648, 0xffffffff, ULONG boundary |
| LX09 FloatSyntaxChip | NumberSpelling → FloatParts | Decimal/hex exponent, decimal point, suffix lexing | `0x1.fp+2`, bad exponent, `1e+foo` |
| LX10 FloatValueChip | FloatParts/format → FloatBits | Correct rounding to the target float/double/long double, supporting subnormals | halfway, overflow/underflow, binary128; no host f64 approximation |
| LX11 EscapeDecodeChip | LiteralBody → CodeUnits | Simple/octal/hex/UCN escapes, target character encoding | Greedy hex, octal at most 3 digits, illegal UCN |
| LX12 CharacterLiteralChip | Prefix/body → TypedCharacter | Plain/wide/extended characters, integer values and multicharacter policy | '\xff', L character, empty literal, multichar |
| LX13 StringLiteralChip | Prefix/body → StringRecord | code units, terminating zero, embedded NUL, element type | "a\0b" length, empty string, wide encoding |
| LX14 AdjacentStringChip | StringSequence → MergedString | Translation-phase merging; handle prefix compatibility and terminator | Adjacent macro output, wide/plain mix, only one trailing zero |
| LX15 LiteralExtensionChip | ExtensionLiteral/mode → Literal | GNU imaginary/standard new suffixes supported per corpus switch | Mode allows/rejects; does not misrecognize identifier |
| LX16 TokenLocationChip | OriginChain/token → TokenSpan | Bind token location to physical/logical/macro origin | Paste-generated token, span after #line |
| LX17 TokenPublishChip | DecodedTokens → TokenRange | Publish the complete payload in order; error tokens available for recovery | EOF, single publication, stable downstream ID |
| LX18 LexErrorChip | InvalidToken → Diagnostic/Recovery | Advance finitely on illegal tokens and preserve spelling; do not panic | Arbitrary-bytes fuzz with no infinite loop |

Standalone tests must verify LX08 across different target widths (synthetic models); FP tests use known bit patterns and a trusted oracle rather than host decimal output. The integrated PP→lex→parse preserves whitespace/locations, but whitespace must not change the meaning of valid tokens.

## Committed literal record (`LiteralRecord`)

The T04→T08 handoff uses a T04-owned committed `LiteralRecord` carrying the per-literal lexical facts plus the `LX08` candidate type (H1 allocation split, accepted in principle 2026-10-04, **not a freeze**). The sem-stage `ConstantRequest` (`node`/`required_kind`) and `ConstantResult` (`legality`) remain T07/T08/T01 shapes; T08 is the sole `constants.records` writer and T04 never writes it. `node` and `required_kind` are **not** on `LiteralRecord`.

**Current operative text — exact ordered fields (user-selected subdecision, CDR rev 45, 2026-10-05; no `/6` freeze, no code/chip authorization):**

```
LiteralRecord {
    token: Option<TokenId>,
    kind: LiteralKind,
    radix: u8,
    suffix: LiteralSuffix,
    value: Vec<u8>,        // big-endian magnitude
    negative: bool,
    spelling: Vec<u8>,
    candidate_type: Lx08CandidateType,
}
```

**M1 enum/scope (same subdecision):**

- `LiteralKind { Integer, Character, String }` — **only `Integer` is produced in M1**.
- `LiteralSuffix { None, U, L, UL, LL, ULL }` — **only `None` is produced in M1**.
- radix domain `{ 2, 8, 10, 16 }` — **M1 decimal only**.
- `Lx08CandidateType` is **symbolic/target-independent**; M1 literals `2` and `3` are typed `Int` with **no bit width**. The `LX08` candidate type is carried on `LiteralRecord.candidate_type`.

### `Lx08CandidateType` M1 candidate vocabulary — selected candidate default (integration, 2026-10-05)

**Candidate default — selected by the M1 integration agent under the user's 2026-10-05 noncritical-decision delegation ("for non-critical decisions adopt the recommended choice directly; ask only for critical decisions"). This is a low-risk integration-selected default grounded in a read-only review of the exercised M1 integer literal subset; it is not an owner/T04 or T01 `[INT]` sign-off, not a `/6` freeze, and authorizes no code.** It refines only the *meaning* of the already-selected `Lx08CandidateType`; it changes **no** field order, type, or count, and reinterprets **no** accepted text.

- **M1-only closed vocabulary:** for the **exercised M1 integer literal subset** (CDR rev 45, 2026-10-05) `Lx08CandidateType` is the one-member closed vocabulary **`{ Int }`**, and the M1 literals `2` and `3` are represented as `Int` — **target-independent, with no bit width**. This is the `candidate_type: Lx08CandidateType` value carried by the committed `LiteralRecord`; it is **not** a target type, ABI type, or `TypeId`, and duplicates no implicit target type.
- **No silent Int defaulting:** literal **forms outside the exercised M1 subset** (non-decimal radix, non-`None` suffix, character/string literals, or any not-yet-specified category) **must not silently default to `Int`**. Until their candidate categories and rules are specified, such forms are classified as an **explicit unsupported/deferred** result or diagnostic — never a fabricated `Int` success.
- **Forward compatibility (append-only):** future C candidate support **appends symbolic members and/or rules** and must **not reinterpret** the meaning of the already-selected `Int` member or repurpose `Lx08CandidateType` for constant-expression purposes (per CDR rev 45: future `RequiredKind` purposes add appended variants/rules).
- **Scope limit:** this does **not** define the complete future C candidate set nor any numeric tag/encoding, and it **freezes nothing**. Features **added later** are **out of M1 scope** and remain governed by their own T04/T08/T01 `/6` co-freeze.

**Still open (deliberately not invented; precise remaining blockers):**

- The **complete `Lx08CandidateType` member set beyond the M1 `{ Int }` subset and every numeric encoding/tag** for `Lx08CandidateType`, `LiteralKind`, and `LiteralSuffix` remain open — a T04/T08/T01 `/6` co-freeze item. The M1 `{ Int }` subset is only the delegated candidate default above; the remaining members and all numeric encodings are asserted nowhere here.
- **All other lexical encoding** (exact token/record wire tags, `Vec<u8>` vs alternatives, the `radix: u8` numeric mapping, and the `negative`/`value` normalization rules) remains open.
- The full `LiteralRecord`/`ConstantRequest` variants and the **T01 + T03/T04/T08 owner co-freeze/sign-off** remain pending.
- No `/5` edit and no `/6` freeze result from this record; `/5` stays current, T04 remains **not signed off**, and **no code is authorized**.

### `LiteralRecord.token` semantics — selected candidate default (integration, 2026-10-05)

**Candidate default — selected by the M1 integration agent under the user's 2026-10-05 noncritical-decision delegation ("for non-critical decisions adopt the recommended choice directly; ask only for critical decisions"). This is a low-risk integration-selected default, not an owner/T04 or T01 `[INT]` sign-off, not a `/6` freeze, and authorizes no code.** It clarifies the *meaning* of the already-accepted `token: Option<TokenId>` field and changes **no** field order, type, or count.

- **`token = Some(t)` iff the committed `LiteralRecord` was emitted from a single committed C token `t`.** For the M1 source integer literals (`2` and `3`), both are ordinary source tokens, so the **M1 candidate uses `Some(committed TokenId)`**.
- **`token = None` is reserved for an explicitly synthesized literal that has no single originating source C token** (for example an adjacent-string-merged literal or a compiler-inserted literal). `None` must record that condition deliberately — it is **not** a placeholder for "not yet resolved".
  - **`None` policy distinction (candidate clarification, not a freeze):** a generated **source** token (a token that exists in the preprocessed source stream, even if produced by macro expansion or pasting) is still a **source token** and yields `token = Some(committed TokenId)`; `None` is for a **generated/synthetic literal** — a literal the lexer itself fabricates with **no single originating source token** (e.g. a compiler-inserted literal or a synthesized terminator literal). The two categories must not be conflated: "generated token" ≠ "synthetic literal".
  - **Beyond-M1 synthesis (deliberately open):** the exact T04 producers authorized to emit a synthetic `None` literal remain **open** and are **not decided** here; beyond-M1 synthesis of source tokens via macro expansion/pasting (the `LX14`/`LX16` provenance carrier) is **out of M1 scope** and awaits its T03/T04 `/6` co-freeze. This clarification fixes only the **generated-source-token vs generated/synthetic-literal** distinction and leaves the synthesis producers open.
- **Never persist a draft, wire reference, or address** in `token` (or any `LiteralRecord` field). `token` holds a **committed durable ID only**; the record is a T04-owned committed record.

**Producer order and reference encoding (candidate):**

- `LiteralRecord` is produced by the literal-decoding chips (`LX07`–`LX15`) and published in order by `LX17 TokenPublishChip`; the record and its referenced C token are written to the **same task's append batch**.
- **Decode input availability — DOC-10 resolution (candidate; not an owner/T04 or T01 `[INT]` sign-off, not a `/6` freeze, no code):** a literal-decoding chip (`LX07`–`LX15`) MUST NOT require a committed C `TokenId` as a decode input. Its decode input is the **committed T03 PP token spelling/kind** (`pp.tokens.{kind,span,spelling}`, per `LexRequest(pp_token_id/range, mode)`) plus the declared mode. The originating `TokenRecord` is written to the **same task's append batch** and is not committed at decode time, and the whole-batch predicted-ID property below resolves links only at commit time, so a committed-C-`TokenId` input would be a decode-time dependency cycle. The C token relation is therefore an **output-side publish-time back-link**: the same-batch typed `RecordLink` is materialized against the batch's predicted token ID and resolved to the durable committed `TokenId` before persistence (next bullets). The alternative **token-first publish/update protocol** — commit the token in an earlier task, decode the literal from the committed `TokenId`, then update/patch the token's `literal` link — is **not selected**: it would need a `lex.tokens` update protocol that is not specified and would replace the same-batch publication candidate; it remains a T04/T01 `/6` co-freeze alternative only if this candidate is rejected.
- If a literal's originating `TokenRecord` is produced in the **same batch** as the `LiteralRecord`, the intra-batch relation MUST be expressed through the T01-frozen typed `RecordLink` append-reference mechanism (the M1 proposal's candidate materialization via `RecordLink` / `LinkTarget` / `RecordDraft::links()`, proposal §3 item 2 / §6.1) — a **same-batch typed record reference**, never a raw draft index/handle stored in the record. `ContinuationRef::OwnBatch` / `ChildRef::OwnBatch` are **not** generic record references; they belong to the continuation/task-child protocol (task-level transient input), so they do **not** describe a token↔literal record relation.
- Before the literal is persisted, that same-batch typed record link is **resolved to a durable committed `TokenId`** and the committed `token: Some(TokenId)` is recorded; no durable `token` value ever points at a draft, wire, or address (consistent with ADR-0002 §6).
- **Reciprocal token↔literal links within one T04 append batch (M1 candidate, not a freeze):** the M1 candidate **may** carry **both** directions of the relation in the **same T04 `AppendRecords` batch** — `LiteralRecord.token = Some(_)` pointing at the originating `TokenRecord`, and that `TokenRecord.literal = Some(_)` pointing back at the `LiteralRecord`. This is a **cycle between two records appended in one batch**, not a cross-task reference. It is a candidate materialization grounded in the M1 proposal's deterministic reserve/resolve approach (§7/§8; phase 2b/2c builds the predicted-ID table before link validation, then phase 2d resolves), and it changes **no** already-accepted field order, type, or count.
  - **`RecordLink::Draft` is NOT treated as already frozen.** The M1 proposal's `RecordLink { expect, target: LinkTarget = Committed(RecordRef) | Draft(DraftRef) }` shape, the `DraftRef` keying, the local-link spelling, and its wire tag remain a **T01 `/6` co-freeze item**; this candidate depends on that mechanism being co-frozen as described below and does **not** assert it as frozen.
  - **Required T01 co-freeze property (candidate protocol condition, not a numeric-ID/encoder choice and not a freeze):** T01 must freeze that, **for the entire own `AppendRecords` batch**, stable record IDs are **pre-reserved/predicted before any typed `RecordLink` is validated or resolved**; **all family/range links are then validated against that predicted-ID table**, and the **committed IDs are persisted atomically** only after validation. Under that property, an intra-batch **cycle** (token↔literal) is resolvable **without topological resolution**, because both endpoints already have predicted durable IDs in the same table; **no ordering dependency** exists between the two appends. This is a **required candidate protocol condition** grounded in the M1 proposal's deterministic reserve/resolve approach — it selects **no** numeric ID, no encoder, and freezes nothing.
  - **Fallback if T01 does not support the property:** if the T01 `/6` co-freeze does **not** establish whole-batch pre-reservation/prediction before link validation (i.e. resolving a link requires an already-committed target), then the M1 candidate **must drop or derive one of the two reciprocal fields before freeze** — either `LiteralRecord.token` or `TokenRecord.literal` becomes **derived/absent** rather than an independently appended reciprocal link — so that no intra-batch cycle requires topological ordering. Which field is dropped/derived is a T04/T01 `/6` co-freeze item, not decided here.
- **Open (exact representation pending T01 co-freeze):** the exact `RecordLink`/`LinkTarget` local-link spelling, its wire-tag value, and its error handling remain a T01 `/6` co-freeze item; no exact `RecordLink` spelling is asserted here.

**Explicitly left to T04/T01 co-freeze (not decided here):**

- The synthetic-literal policy **beyond M1** — which T04 producer (e.g. `LX14` adjacent-string merge, `LX16` paste/provenance) may emit `token = None`, and any typed provenance carrier for synthesized literals — remains open pending T04/T01 co-freeze.
- The **source-span relation and error codes** (which committed token/span a `Some` token must belong to; the token↔literal consistency check; whether a `Some` `token` whose committed record is missing or from a different source is a commit/validation error) remain open pending T04/T01 co-freeze.
- The exact numeric error/diagnostic codes and hash encoding for the above remain T01 `/6` details.

## M1 lexical vertical-slice contract candidate (T03 PP token → T04 C token/literal committed records)

**Status: candidate contract material for the M1 vertical slice only — NOT an owner/T04 or T01 `[INT]` sign-off, NOT a `/6` freeze, and NOT code/chip authorization.** This section records an M1-only lexical slice candidate: a committed T03 PP token flow into a committed T04 C token and, for M1 integer literals, a committed T04 `LiteralRecord`. It is grounded in the already-recorded accepted subdecisions (rev 44/45 `LiteralRecord` fields; rev 45/47 token candidate default) and in the read-only M1 proposal/CDR mechanism; it invents **no** numeric tag, wire code, hash, or enum encoding. Every exact encoding remains a **T01 `/6` co-freeze** item. `/5` stays current, `/6` stays unfrozen, T04 remains **not signed off**, and no other file was edited.

### Slice boundary and M1 scope

- **In scope (M1-only):** the T03→T04 flow for the single-source M1 fixture: 12 committed PP tokens plus one EOF (`M1-PP-04`/`M1-PP-06`) → C tokens with committed T03 PP-span reuse → integer literal records for the decimal, no-suffix source literals `2` and `3` (`M1-LX-01`–`M1-LX-07`).
- **M1 integer / no suffix / decimal only:** `LiteralKind::Integer` is the only produced kind; `LiteralSuffix::None` is the only produced suffix; `radix == 10` is the only produced radix; the M1 candidate type is the closed one-member vocabulary `{ Int }` (target-independent, no bit width), per the `Lx08CandidateType` M1 candidate default above.
- **Explicitly unsupported/deferred (non-M1 forms; must not silently succeed):** non-decimal radix (`2`/`8`/`16`, `LX05`), any non-`None` suffix (`U`/`L`/`UL`/`LL`/`ULL`, `LX06`), floating and hexadecimal-float literals (`LX09`/`LX10`), character literals (`LX12`), string literals (`LX13`), adjacent-string merging (`LX14`), and literal extensions such as GNU imaginary (`LX15`). Each is classified as an explicit unsupported/deferred result or typed diagnostic — **never** a fabricated `Int` success and **never** a silent `Int` default. Their candidate categories, carriers, and rules remain a T04/T08/T01 `/6` co-freeze item.
- **Non-M1 structural deferrals:** multi-source/include expansion, macro/paste provenance, adjacent-string-merged tokens, and any synthesized literal are outside the M1 slice; the typed T04 provenance carrier that `LX14`/`LX16` need is a T03/T04 `/6` blocker (see `TokenRecord.span` note below), not provided here.

### T04 task request/result payload (candidate shape; identifiers, not numeric tags)

The M1 slice uses the already-recorded T04 protocol line `LexRequest(pp_token_id/range, mode)` → `TokenResult`, the T04→T08 committed-literal flow (`const.literal-decode`, proposal/CDR), and the T04 acceptance labels `literal_record_committed`/`literal_t04_t08_handoff`; the concrete T04 token-classification/literal-decode task-kind spellings are **not** fixed anywhere yet and are **not invented here**. The following **candidate** payload fields are descriptive only. Field names below are not frozen; the exact payload variant spellings, task-kind vocabulary, `RecordRef`/`RecordLink` encodings/tags, task stage/depends-on typing, and every numeric code remain **T01 `/6` co-freeze** items (no tag is asserted).

- **Input (T03 → T04) candidate:** the committed T03 `PpTokenId`(s)/range and the declared mode/target config, per the existing `LexRequest(pp_token_id/range, mode)` protocol line; the input references **committed** T03 PP tokens only (no same-tick PP draft).
- **Fragment/child request candidate:** a decode request referencing the committed PP token spelling/kind (`PpNumber`/`Identifier`/`Punctuator`/`CharConstant`/`StringLiteral`/`Eof`) and the declared mode. For literal decode the decode input is that **committed T03 PP spelling/kind** — **not** the C `TokenId` (DOC-10 resolution above): the originating `TokenRecord` is written to the same task's append batch and is not committed at decode time, so a committed-C-`TokenId` input would be circular. The C `TokenId` appears only as the publish-time back-link (`LiteralRecord.token`), resolved from the same-batch typed `RecordLink` before persistence. Numeric parsing may use typed child tasks; multiple tokens may merge into one string.
- **Output/result candidate:** a committed C `TokenId` reference (`RecordRef::Token`) for token classification, plus, for a decoded integer literal, a committed `RecordRef::Literal` reference. The result carries **references only** (`RecordRef`-only payload); it does not re-embed record bodies, and the value/legality fields are not invented here.

### C Token fields (candidate view)

The M1 C token record candidate matches the proposal `TokenRecord` field set (no new field invented):

```text
TokenRecord {
    kind: TokenKind,                 // M1 closed subset exercised: keyword/identifier/punctuator/integer/eof
    span: SpanId,                    // committed T03-owned PP span; T04 writes NO span
    name: Option<NameId>,            // interned identifier name (identifier/keyword tokens)
    literal: Option<RecordLink<Literal>>, // T04-owned committed LiteralRecord reference (NOT a ConstId); typed draft link, resolved pre-apply. Candidate; the exact link spelling/tag is T01 /6 co-freeze
    flags: TokenFlags,               // exact bit/flag encoding open
}
```

- **`span` reuse (M1 exact):** the token's `span` references the **committed T03 PP span**; T04 appends **no** `sources.spans` record and writes no span identity. This is exact only for the one-PP-token→one-C-token M1 fixture; `LX14`/`LX16` need a typed T04 provenance carrier that is **not** provided here (T03/T04 `/6` blocker).
- **`literal` reference:** points at a **committed T04-owned `LiteralRecord`**, never a `ConstId`; T08 owns `constants.records` and consumes the literal via a committed `RecordRef::Literal`.
- **`TokenKind`/`TokenFlags` numeric encodings are not invented** and remain a T04/T01 `/6` co-freeze item.

### Token-to-literal link validation (candidate)

- A `LiteralRecord.token = Some(t)` is well-formed only if `t` is a **committed** C `TokenId` in the same source/TU, and the committed token's classification is consistent with the literal kind (for M1, an integer literal's originating token has a numeric/pp-number origin and integer classification).
- **Same-batch relation:** when the originating `TokenRecord` and the `LiteralRecord` are produced in the **same task batch**, the relation must be expressed through the T01-frozen **typed `RecordLink` / append-reference mechanism** (`RecordLink { expect: RecordFamily, target: LinkTarget }`, `LinkTarget = Committed(RecordRef) | Draft(DraftRef)`; `RecordDraft::links()`), **not** a raw draft index/handle stored in the record and **not** the task-level `ContinuationRef::OwnBatch`/`ChildRef::OwnBatch` (those belong to the continuation/task-child protocol). The `RecordLink::Draft` shape is **not treated as already frozen** (see the `LiteralRecord.token` section); it depends on the T01 co-freeze property below.
- **Decode-time input (DOC-10 resolution):** the same-batch relation is **output-side only**. The decode request reads the committed T03 PP spelling/kind; `token = Some(t)` is produced by resolving the batch's predicted token ID at commit time. No decode request may depend on a committed C `TokenId` from its own batch.
- **Reciprocal same-batch cycle (candidate):** the M1 candidate **may** express the relation in **both** directions within one T04 `AppendRecords` batch (`TokenRecord.literal` → `LiteralRecord` and `LiteralRecord.token` → `TokenRecord`). Resolving such a cycle requires the T01 co-freeze property that **the entire own batch's stable IDs are pre-reserved/predicted before any typed `RecordLink` is validated/resolved**, so no topological resolution is needed. If T01 does not establish that property, one reciprocal field must be dropped/derived before freeze.
- **Resolution before persistence:** the same-batch typed link is resolved to a durable committed `TokenId` before the record is persisted; no durable `token` (or any `LiteralRecord` field) ever points at a draft, wire, or address.
- **Open T04/T01 co-freeze:** the exact `RecordLink`/`LinkTarget` local-link spelling, its wire-tag value, the token↔literal consistency predicate and which committed span/source a `Some` token must belong to, the missing/mismatched-token validation error (commit error vs chip diagnostic), and all numeric error/diagnostic codes. No validation error name is asserted here.

### NameId interning (candidate)

- Identifier (and keyword) tokens intern their spelling through the T04-owned `names.entries` intern store; **identical spelling yields the same stable `NameId`** (`M1-LX-02`). `NameId` is a stable newtype ID; no pointer/address participates.
- The interning boundary is the M1 deterministic lookup-first (`NamePlan`) mechanism; the exact intern-entry shape, the `NameDraft` dedup idempotence rule, and any numeric `NameId` encoding remain **T01 `/6` co-freeze** items. `names.entries` is T04-only (T03/T06 read-only; mandatory allowlist).

### Lexical diagnostics and manifest reads/writes still needing T01 co-freeze

- **Diagnostics (candidate obligations, no codes asserted):** unknown character (`M1-NEG-04`, `LX01`/`LX18`), malformed pp-number/float syntax (`M1-NEG-05`, `LX09`), unterminated literal (`M1-NEG-06`, `LX12`/`LX13`), literal value beyond every candidate (`M1-NEG-07`, `LX07`/`LX08`). Each must advance finitely, preserve spelling, and not panic. The exact diagnostic class/category vocabulary, numeric codes, and hash encoding remain **T01 `/6`** details.
- **Reads (field-scoped, upper bound only):** `tasks.active.{id,kind,payload}`; `config.{target,dialect}` when the rule requires it; the committed T03 `pp.tokens.{kind,span,spelling}` of the referenced PP token(s); the committed `sources.spans` (read-only, reused, never written); the committed `names.entries` for the lookup-first intern check.
- **Writes (chip-owned append/patch + wires only):** `lex.tokens` (own append area), `lex.literals` (own append area), `names.entries` (own intern append), the chip's own output slot, and `wires.proposals[ChipId]`; diagnostics go through the `Fail`/`DiagnosticDraft` path (the exact name — `DiagnosticDraft` vs `DiagnosticProposal` — is an open T01 `/6` co-freeze item). T04 writes **no** `sources.spans`, **no** `constants.records`, and does not advance the phase.
- **Still needing T01 co-freeze (exact encodings/fields, not invented here):** the per-chip field-level read/write manifests (which `lex.*`/`names.*` fields each `LX` chip declares), the `TaskKind`/`StageId` assignment and routing for the lexical task kinds, the `lex.literals`/`lex.tokens` append-writer allowlist enforcement, the `RecordFamily`/`RecordRef` tags for `Token`/`Literal`/`Name`, and the canonical encoder/snapshot participation for `TokenRecord`/`LiteralRecord`.

### Ordered publication (candidate)

- **`LX17 TokenPublishChip` publishes the complete payload in source order**: the 12 C tokens plus exactly one EOF, in committed append order, with stable downstream `TokenId`s (`M1-LX-06`). `LiteralRecord`s are published in order by `LX17` as well; a literal record and its referenced C token are written to the **same task's append batch**, and the literal's `token` back-link is resolved from that batch's predicted token ID at commit time (DOC-10 resolution above). The decode input for the literal was the committed T03 PP spelling/kind, so no decode or publish step waits for a committed C `TokenId` from the same batch.
- **Required integration fixture — decode input availability and publication order (candidate, DOC-10):** the M1 acceptance inventory must add an integration fixture (exact ID/registration remains an integration/T01 item, not invented here) covering: (a) the literal-decode request is dispatched only after the referenced T03 PP token is committed, and the decode reads that committed PP spelling/kind — it is never handed or made to wait for a committed C `TokenId`; (b) after the T04 append batch commits, `LiteralRecord.token` equals the committed `TokenId` of the C token appended in that same batch (the resolved back-link), with deterministic token/literal publication order matching append order. The fixture is **required pending**, not a pass.
- Publication order is deterministic (append order = committed `TokenId`/`LiteralId` order); no hash-map iteration or address participates. Error tokens remain available for recovery and do not disrupt the ordering of the following committed tokens.
- **Open T01 co-freeze:** whether publication is one append proposal per token or a batched `AppendRecords { task, batch }`, the exact ordering/publish rule, and the single-publication/stable-ID contract all remain T01 `/6` items.
