# T13: Verification Chips, Replay, and Differential Checking

Prerequisite T01, directory `chips/verify/`. Read each stage's records and freeze config, oracle inputs (sampled and injected by the Host); write verification facts/proposals. Chips must not execute GCC/programs/file reads; after execution the T00 Host feeds structured evidence into pins. The real report computing the final pass rate still belongs to T00; a verification chip passing does not mean the entire compiler passes.

Test evidence must cover both rule correctness and paradigm correctness. Invalid C may be used for diagnostic/recovery tests, without comparing arbitrary UB output; the original assertions of the frozen GCC torture are not to be deleted on one's own under this principle.

### VF06 `TypedAstInvariant` — M1 registration and fixture checklist

VF06's **M1 role is fixed** (after the committed T07 `SemRecord`s, before T09 lowering). Its **exact registered task kind/stage/phase/interface is unresolved (T01/T13)** and is not fixed here. Grounded only in the current docs, the following items are forced by the **M1-minimal conversion scope** (identity/no-conversion only) and by "VF06 checks M1 typed-fact/required-conversion completeness":

1. **Registration (UNRESOLVED — T01/T13).** The task kind, stage name/ordinal, phase, layer, verification result kind, and input/output interface that place VF06 between committed T07 `SemRecord`s and T09 lowering are **not defined today**. 2. **Typed-fact completeness (forced by the committed-`SemRecord` decision).** For the M1 fixture, VF06 must be able to check that **every checked `NodeId` the lowering path consumes has exactly one committed `SemRecord`** (the `SemRecord` = committed materialization of `CheckedNode`, one per `NodeId`, rev 42) and that the required per-node typed fact is present: `type` (`TypeId`), `ValueCategory`, and `EffectMask` on each checked node, plus the `FunctionDefinition` signature `TypeId` and the `Return` operand type. Fixture: a positive M1 case where all checked nodes carry their typed fact; negative cases for a **missing typed fact** (a lowerable node with no committed `SemRecord`/typed fact) and for an **unchecked node offered to lowering**.
3. **Required-conversion completeness (forced by the CDR §F3 obligation, M1-minimal scope).** VF06 must check **completeness**, i.e. that a *required* conversion exists, distinct from *uniqueness* (`at most one` plan per `(node, role)`). Under the **M1-minimal conversion scope** the only M1-permitted conversion behavior is the **identity/no-conversion rule**; the M1 fixture `2+3` in `int` has `int` operands and `int` result and therefore requires **no** operand conversions, and the `int`-to-`int` return is **identity** (`M1-TY-09`, `M1-SE-02/03`). Fixture obligations therefore forced by M1-minimal scope: (a) **identity/no-conversion accepted** — a recorded `Identity` plan where the owner records a no-op must not be flagged as missing; (b) **no false required-conversion** — VF06 must **not** require a conversion for the M1 `int`/`int` case (this is the "must not over-enforce" rule; M1 `2+3` requires none); (c) **missing required conversion flagged** — a case where the CDR §F3 table would require a plan (e.g. a `Return` whose operand type differs from the function return type, or `BinaryExpression` operands differing from the usual-arithmetic common type) and no plan is present must be a verification failure. Fixture: a positive case where T09's required conversion facts are present on the committed `SemRecord`s; negative cases for a **missing conversion fact** and for a **dangling/uncommitted link** offered to the checker.

## Framework-Level Mechanical Constraints Already in Place (Not the CompilerBus Implementation)

`cc-silicon::RestrictedChip`/`silicon_chip!`/`ChipAdapter`/`ProjectedChip` and `Motherboard::install_projected` provide a strict chip computation path: a chip has only `&Input` and typed Output, with no Bus access; the macro accepts only unit structs and performs a size=0 const assert; the adapter is explicitly responsible for projection and proposal submission. The old `LogicChip` still exists, retained for compatibility, and must not be used in new compiler chips.

The corresponding CI tests should be retained:

1. rustdoc compile-fail: field declarations, direct bus references, and modifying inputs should all fail to compile.
2. positive doctest: the macro declares the chip size as 0, and the computation result is normal.
3. integration test: restricted chip recomputes deterministically; proposals are submitted only through the adapter; wire reset/latch is still the motherboard's responsibility.
4. adapter permission test: changing a declared output field succeeds, and undeclared registers and register fields remain unchanged field by field.
5. application-level AST lint/dependency audit: **partially implemented** by `tools/chip-lint/` (below) — Host API dependency detection and strict-fail on unanalyzable macro/dynamic paths are in place; the **dependency allowlist audit and full cross-module chip-call detection remain future work** (audited coverage boundaries recorded below).

The AST-based checker is implemented under `tools/chip-lint/`. It has a dedicated test suite and scans a caller-specified chip-source directory. Its formatting, Clippy, and tests run in `.github/workflows/ci.yml`; no application chip tree exists in this framework-only repository to scan yet.

Current executable strict-path gates in the framework crate and lint tool:

```sh
cargo test --doc
cargo test --test paradigm
cargo clippy --all-targets -- -D warnings
cargo test --manifest-path tools/chip-lint/Cargo.toml
cargo run --manifest-path tools/chip-lint/Cargo.toml -- <compiler-chip-directory>
```

The checker enforces seven rejection categories: opaque macros in `compute` (expression and item macros) and unexpanded top-level macros other than `silicon_chip!`; unresolved or indirect bare calls; `unsafe` blocks; common Host/nondeterministic imports and expression paths; legacy `LogicChip` impls; non-unit `*Chip` structs; and obvious chip-to-chip execution calls (`tick`/`clock_tick`/`execute_layers`, or any method on a same-file chip receiver). It also strict-fails on parse errors, on `silicon_chip!` declarations that do not implement `RestrictedChip`/target their declared struct, and on chip impls without `compute`. This is a conservative AST lint, not a proof. The 2026-10-05 audit records its specific coverage boundaries: (a) **same-file symbol scope** — `known_functions`/`known_chip_names` are collected per file, so a chip method call whose name is not one of the listed execution methods and whose chip is declared in another file/module is not flagged, while cross-file helper calls are conservatively flagged as unresolved; (b) **qualified-call acceptance** — multi-segment call paths (e.g. `OtherChip::compute()`, `crate::helpers::f()`) are treated as resolved without further audit, and the chip-receiver check matches only bare-ident receivers; (c) **cross-module detection gap** — because (a) and (b) are per-file, the item-5 "cross-module calls between chips" prevention is not implemented; imports, re-exports, and `mod` declarations are not resolved; (d) **no dependency allowlist** — external crate imports are rejected by root rather than checked against an approved list, and there is no `Cargo.toml` dependency audit. It also cannot resolve all Rust aliases, method dispatch, re-exports, or transitive effects in called helpers/dependencies. Strict CI must still pin/allowlist chip-crate dependencies, keep Host code outside the chip crate, review helpers, and run deterministic replay tests; add reviewed rules/tests before widening an allowlist.

These guarantees have clear boundaries: Rust can constrain RestrictedChip code so it cannot see the Bus, but the current ChipAdapter still obtains a full Bus reference, so adapter field-level reads/writes cannot be guaranteed at compile time; to upgrade this layer into a strong guarantee, the CompilerBus schema needs to generate a per-chip private projection and typed patch setter. Pure functions are also not proven globally side-effect-free by the macro; crate dependency isolation, lint, and replay tests are still required.

## Verification Engineering Deliverables (Non-Chip Host Tests)

1. Per chip: all tests in the case table, at least one mutation regression (the test can fail when the rule is deliberately broken).
2. Per stage: real upstream/downstream signal integration, cross-tick result persistence, unauthorized stores unchanged.
3. type/layout/ABI: reference probes for the same target and two-way mixed linking.
4. preprocess/token/typed AST/IR: stage dumps support first-divergence localization, dumps are stable and do not depend on host pointers.
5. optimize: generate well-defined programs, before/after IR and target-execution differential; fenv/NaN/alias and other high-risk items in separate cases.
6. extensions: positive/negative tests in standard/GNU mode, and each corpus failure's owner chip IDs are traceable.
7. regression: the original GCC cases must not be modified; reduced cases and proptest seeds are retained; the full matrix is rerun.

ProofObligation/Counterexample class chips may continue to be added, but it must not be claimed that the current task has completed a formal proof. 99% is engineering acceptance on a frozen test corpus, and does not mean 99% of all C programs are correct or that there are "mathematically no bugs".
