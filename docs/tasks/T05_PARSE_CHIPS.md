# T05: Taskified Parsing Chips

Prerequisite T01; the interface depends on T04 tokens and T06 scope/name/type requests. Directory `chips/parse/`. Read lex/parse frames and typed service results; write AST/declarator/frame records and proposals; do not perform type compatibility/ABI itself. During parse, scope and typedef visibility must be maintained, so it is not a pipeline fully isolated from the symbol phase.

Unified `ParseRequest(production, token_cursor, scope_id, context, binding_power)` → `ParseResult(node/declarator, next_cursor)`. All nesting goes through child tasks/continuations. Without a typedef query result, it must not guess from the string; a T01 implementation may first return a declaration AST, but during parse it must register enough name categories.

**OPEN-01 startup-order candidate (docs-only; proposal §24.14; not a T05 owner signoff and not frozen).** The candidate M1 order commits the `TranslationUnit` **root** early — in the registered `parse.TranslationUnit` task's first commit-visible batch, after the whole token stream (incl. EOF) is committed and before the external-declaration loop — and the accepted `parse.TranslationUnit -> symbol_type.scope-enter` edge fires on that committed root while the parse task is `Waiting`; parse then resumes with the committed file `ScopeId`, so the parse-time scope/typedef visibility required above is preserved. The fallback (explicit M1 no-scope parse path) and the `M1-START-01` no-prebuilt-scope startup fixture are recorded in the proposal §24.14. Item F point 6 carries the T05-side details; all encodings remain T05/T01/T06 `/6` co-freeze.

## Operative amendments (T05/T01/T02 decisions)

This section records the **user-accepted T05/T01/T02 subdecisions** (CDR `rev 42`/`rev 43`/`rev 47`, 2026-10-05) as operative T05 text. It also records **integration-selected candidate defaults under explicit user delegation** (2026-10-05) that are **not** T05 owner, T06 owner, or T01 `[INT]` sign-offs: the `ParseContext` vocabulary (item E) and the `TranslationUnit` parse-task completion carrier (item F). It does **not** amend `/5`, freeze `/6`, or authorize any chip or code. The overall T05 bundle remains **PENDING**; the unresolved items are listed at the end.

### A. Continuation and join (CDR rev 42/43)

1. **Join is a commit-apply invariant; no new CT07 committed carrier/family.** The parent waiting/resume join is realized in the **commit-apply phase** (the only component that may mutate task state before latch). **CT07 is decision-only** — it computes/marks the join and mutates nothing. No new committed CT07 carrier, store, or record family is introduced for the join.
2. **Await-all children terminal before the parent decision.** On resume, the parent decision is taken only after **all** committed children are terminal: if **all** committed children are `Completed`, the parent returns to `Ready`; if **any** committed child `Failed`, the parent becomes `Failed` **exactly once** and is **never** set `Ready`.
3. **Join reinsertion target.** The resumed parent is reinserted into its **own canonical stage queue `stage_queues[stage_of(parent.kind)]`** — the parent task's **kind**, not `stage_of(parent.continuation.production)` — not `tasks.ready`, and not by CT09/CT10. The realization must handle a parent whose `continuation` is **absent** (a parent task kind with no parse continuation is still resumable by its kind). The parent is selected next tick.
4. **`WaitSet`-only awaited children; no continuation `awaited`.** `TaskState::Waiting(WaitSet { children, host_request })` is the **sole** source of awaited-child IDs. `ContinuationRecord` carries **no** duplicate `awaited`. This is the formal `/6` supersession of the old T01 §4 continuation-`awaited` wording; **T01 §5 and `/5` are unchanged** (no `/5` edit).

### B. Continuation exact ordered fields (CDR rev 43)

The candidate `ContinuationRecord` **exact ordered fields/shapes** are accepted:

`production: TaskKind`, `cursor: TokenId`, `context: ParseContext`, `binding_power: u16`, `scope: Option<ScopeId>`, `parent: Option<NodeId>`, `partial_children: Vec<NodeId>`, `next_child_ordinal: u32`, `previous: Option<ContinuationId>`.

There is **no `awaited`** field. All durable references point to **committed IDs only**. The `RecordRef` numeric wire tags and the `RecordFamily` ordinals remain **separate inventories**; their exact numeric encodings remain a **T01 `/6` freeze detail** (not fixed here).

### C. OwnBatch pre-apply validation (CDR rev 43)

`ContinuationRef` (`Committed`/`OwnBatch`) and `ChildRef` (`Committed`/`OwnBatch`) are same-task only and are validated in the **no-mutation pass, before apply**:

- a `ContinuationRef::Committed(id)` requires the `ContinuationId` to exist and be live;
- a `ContinuationRef::OwnBatch(k)` requires `k` within this task's own `AppendRecords` draft range **and** the draft family `Continuation` (**phase 1**);
- a `ChildRef::Committed(id)` requires the `TaskId` to exist and be a valid committed child of this task;
- a `ChildRef::OwnBatch(k)` requires `k` to index this task's own `Enqueue` list (**phase 2b**, after the task's own enqueues are known).

A violation is `ContinuationRefInvalid`/`AwaitChildrenRefInvalid` and rejects the **whole batch** as a `CommitError` **before any mutation**. The error **numeric codes and hash remain T01 `/6` details**.

### D. Parse depth (CDR rev 47 — integration-selected default under user delegation, **not** frozen owner signoff)

Parse depth reuses `limits.max_task_depth`; it counts **parser continuation/child frames only** (not total bus tasks) and is detected **before any child enqueue for the descent**; excess is the `ParseDepthExceeded` **chip diagnostic** (no new limit, no Rust stack overflow). This is an **integration-selected candidate default under explicit user delegation** (2026-10-05), **not** a T05 owner signoff or a T01 `[INT]` acceptance, and it remains **pending final `/6` co-freeze**.

### E. `ParseContext` vocabulary (integration-selected candidate default under user delegation, **not** frozen owner signoff)

Under the **explicit 2026-10-05 user delegation** ("for non-critical decisions adopt the recommended choice directly; ask only for critical decisions"), the M1 integration agent selected the **proposed closed vocabulary** from the M1 proposal:

`ParseContext { TranslationUnit, ExternalDecl, Specifier, Declarator, ParameterList, Block, Expression, Assignment, Unary, Primary }`

Meanings, kept distinct:

- **`context`** is a **grammar category / entry constraint** evaluated at the **saved cursor** — it states which grammar entry the resumable parse frame is in. It is **not** a task identifier.
- **`production: TaskKind`** identifies the **registered parser task to resume**.
- **`context` must not be derived from or elided with `production`** (and vice versa) absent an **explicit frozen one-to-one mapping**; no such mapping is fixed here.
- The **Expression** and **Assignment** contexts may use the `binding_power` field (precedence-climbing); this does not extend `binding_power` meaning to any other member.

This is an **integration-selected candidate default under explicit user delegation** (2026-10-05), **not** a T05 owner signoff or a T01 `[INT]` acceptance.

Remaining **T05/T01 co-freeze** for this item (all still open): the mapping of a parser continuation/task to a `context`; whether each listed member is actually exercised; and all **canonical discriminants, encoding, and unknown-tag error** handling. The existing accepted continuation ordered fields (B) and the `WaitSet` / join / `OwnBatch` decisions (A, C) are **preserved unchanged**.

### F. `TranslationUnit` parse-task completion carrier and File-Enter stage-edge exactly-once (integration-selected candidate default under user delegation, **not** frozen owner signoff)

Under the same **explicit 2026-10-05 user delegation** ("for non-critical decisions adopt the recommended choice directly; ask only for critical decisions"), and grounded in a **read-only TU-carrier audit** of the frozen `/5` code (which has `TaskState::Completed(ResultId)`, the generic `ResultValue::Record(RecordRef)`/`RecordRef::Node(NodeId)` variants, and no `parse.TranslationUnit` registration), the M1 integration agent selected this **candidate default** for how the upstream committed-`TranslationUnit` carrier (open; see item H) is realized:

1. **Completion fact.** The registered `parse.TranslationUnit` parse task completes successfully with its committed `TaskState::Completed(ResultId)` — the existing committed T01 terminal task fact.
2. **Result typing.** The `TaskState::Completed(ResultId)` result uses the **existing generic `ResultValue::Record(RecordRef::Node(root_node_id))`** payload, i.e. the generic single-record foundation variant carrying the committed TranslationUnit `NodeId`.
3. **Trigger ordering.** Only **after both** (a) the task completion and (b) the TranslationUnit `NodeRecord` commit are visible does the deterministic stage edge enqueue — exactly once — the `parse.TranslationUnit -> symbol_type.scope-enter` event, carrying the **committed `NodeId`**.
4. **No new schema.** **No** new typed `TranslationUnit` `ResultValue` variant; **no** new node kind/family; and **no** task-kind-only derivation (the task kind identifies the *operation*, not the root `NodeId`, so the committed root `NodeId` must come from the committed record/result, not from the kind alone).

This is an **integration-selected candidate default under explicit user delegation** (2026-10-05), **not** a T05 or T01 owner signoff, **not** a T06 signoff, and **not** a frozen `/6` item. It is **not** a committed-TU schema freeze. It **preserves** the previously accepted File Enter stage edge (`parse.TranslationUnit -> symbol_type.scope-enter`, item E / T06) and all other T05 decisions.

5. **Stage-edge cannot rely on `Completed(ResultId)` alone (delegated candidate clarification).** The committed `TaskState::Completed(ResultId)` fact (point 1) is **not sufficient** to drive the exactly-once stage edge by itself: the `ResultId` is a durable handle, not a consumed-delivery claim, and matching on the task kind or on completion status alone cannot distinguish an already-delivered completion from a fresh one. The candidate therefore states the stage edge as a **result-consumption** condition over the **registered `parse.TranslationUnit` task's own successful, still-unconsumed `ResultRecord`** whose value is the point-2 generic `ResultValue::Record(RecordRef::Node(root_node_id))`. Concretely:

   - **Precondition.** The registered `parse.TranslationUnit` task is terminally `Completed`, and it holds a **successful, unconsumed** `ResultRecord` in the committed bus whose value is `ResultValue::Record(RecordRef::Node(root_node_id))` with a **committed** root `NodeId`.
   - **Atomic effect.** In the same **commit-visible transaction**, the stage edge **consumes that one result** and **enqueues exactly one** T06 `symbol_type.scope-enter` task carrying the **committed root `NodeId`**. Consumption + enqueue are one commit-visible unit; the edge fires **exactly once** for that result, and no second delivery may be produced from the same result.
   - **Fallback if atomicity is unavailable.** If the `/6` frozen commit machinery **cannot** atomically combine *result consumption* with *task enqueue* (i.e. no single commit-visible transaction covers both), then **T01 must define an equivalent persistent delivery claim** — a durable consumed/delivered marker on the result or an equivalent frozen mechanism — so that exactly-once delivery is still enforced. The durable claim is **not by itself** the equivalence: T01 must also define the recovery relation that excludes a consumed-but-not-enqueued state and re-delivery across retries (the retry/error recovery semantics below are **open**). This document **does not** invent that mechanism and **does not** freeze it. **Qualified by point 6 for the File-Enter edge:** that edge is append-triggered while the TU task is still `Waiting` (no terminal `Completed` result exists at trigger time), so no result is consumed and exactly-once is structural; neither this fallback nor the point-5 consumption scheme is required for it, and both remain candidates for completion-triggered/other result hand-offs.
   - **No new schema.** The clarification adds **no** new `ResultValue` variant, **no** new result/record marker family, and **no** new node kind. The consumed/unconsumed distinction is **not** introduced here as a concrete field; it is left to the T01 `/6` freeze. The `/5` consumption caveat applies: `consume_result` returns a **clone of the whole `ResultValue`** with **no partial claim API**, and `consumed` already governs **general T01 result hand-off**, so this edge needs a claim consumed **only** by it or **proven non-overlap** (recorded in T06 item 7d; remains co-freeze).

   The **exact consume/enqueue envelope** (the precise transaction boundary, the consumed-state representation, and the write-scope manifest of the consumption) is **open**. The **retry/error recovery** semantics (what the stage edge does if the enqueue fails, if the result is absent/unsuccessful, or if the commit is retried, and how re-delivery is prevented across retries) are **open**. The **task typing** of the T06 scope-enter task enqueued by this edge is **open**. All three are **T05/T01/T06 co-freeze** items and are **not** fixed here.

**Remaining T05/T01/T06 co-freeze** for this carrier (all still open): the exact `TaskKind` identity/registration of the `parse.TranslationUnit` task; the exact `ResultValue` typing (whether the generic `Record` variant is retained versus another frozen representation); duplicate-edge suppression; the precise trigger/commit ordering grammar; and the T06 enqueue payload manifest. Additionally open per point 5: the **exact consume/enqueue envelope**, the **retry/error recovery** semantics of the stage edge, and the **task typing** of the enqueued T06 scope-enter task. If the `/6` machinery cannot atomically combine consumption and enqueue, **T01 must define an equivalent persistent delivery claim**; this is left to T01 and not specified here.

6. **Early TU-root commit order — OPEN-01 resolution candidate (2026-10-05; delegated candidate default under explicit user delegation — NOT a T05 owner signoff, NOT T01 `[INT]` acceptance, and NOT frozen).** The candidate M1 startup order is: (a) the whole token stream including EOF is committed in the `lex` stage; (b) the job bootstrap enqueues the registered `parse.TranslationUnit` task (no scope created); (c) the task's first commit-visible batch appends exactly one `TranslationUnit` root `NodeRecord` (`parent: None`, range = first committed token..committed EOF; empty TU = empty range at EOF) and the deterministic `parse.TranslationUnit -> symbol_type.scope-enter` edge enqueues exactly one T06 scope-enter task carrying that **committed** root `NodeId` (exactly once per root append); (d) the TU parse task is `Waiting` on that child while it dispatches (a ready `parse` task would otherwise precede the `symbol_type` task under the `(stage ordinal, …)` dispatch order) and resumes only after the file `Enter` is committed; (e) parse then continues with the committed file `ScopeId` (continuation `scope: Some(…)`), preserving the parse-time scope/typedef dependency above with **no** no-scope carve-out. This **qualifies point 3 for the File-Enter edge only**: the edge triggers on the committed root append, **not** on terminal task completion; points 1–2 (terminal `Completed(ResultId)` + generic `ResultValue::Record(RecordRef::Node(root_node_id))`) remain for downstream consumers that need the complete TU. It also makes the File Enter exactly-once **structural** for this edge (one root append per TU), so point 5's `ResultRecord.consumed` claim is **not required for the File-Enter edge**, and neither is point 5's atomic consume+enqueue effect or its persistent-delivery-claim fallback (they remain candidates for completion-triggered/other result hand-offs; OB-11/OB-50 stay open until co-freeze). **Fallback if rejected:** the explicit M1 no-scope parse path plus the `M1-START-01` no-prebuilt-scope startup fixture, both specified in proposal §24.14. **Still open:** the edge-enqueue realization (same-batch link vs T01 commit-apply hook) and payload encoding, duplicate-root validation, the root-range/descendant invariant, and the bootstrap task kind/stage (OB-39) — all T05/T01/T06 `/6` co-freeze.

### G. M1 parser candidate contract for `int main(void){return 2+3;}` (integration-selected candidate default under explicit user delegation, **not frozen owner signoff**)

Recorded under the same **explicit 2026-10-05 user delegation** ("for non-critical decisions adopt the recommended choice directly; ask only for critical decisions"), grounded **only** in the already-existing M1 proposal inventory (`M1_PART_A_CONTRACT_PROPOSAL.md` §5: `NodeKind`/`NodeRecord`, `NodeDraft`, `ContinuationDraft`, `ParseContext`) and the existing M1 vertical acceptance rows (`M1-PA-01`–`M1-PA-09`). It is a **concise M1-scoped parser candidate**, an integration-selected candidate default — **not** a T05 owner signoff, **not** a T01 `[INT]` acceptance, **not** a schema freeze, and it authorizes no chip or code. **No new parser node, task kind/ID, or numeric code is invented here;** every unresolved identity/encoding is marked as **T05/T01 co-freeze**. It **preserves** items A–F unchanged.

1. **Minimal `NodeKind` inventory (candidate subset of the proposal's closed list).** The canonical source `int main(void){return 2+3;}` exercises these kinds: `TranslationUnit`, `FunctionDefinition`, `TypeSpecifier`, `Declarator`, `ParameterList`, `Block`, `Return`, `BinaryExpression`, `IntegerConstant`, `Identifier`. It is classified as a **function definition, not a `Declaration`** (`M1-PA-02`), and it contains **no expression statement**, so `Declaration`/`ExpressionStatement` are part of the closed proposal list but are **not exercised by the canonical source**. `UnaryExpression` is reserved for the M1 boundary fixture `M1-PA-08` (`2+ +3`, unary plus) but is **not** exercised by the canonical source; `ErrorRecovery` is reserved **only** for recovery (`M1-NEG-*`) and carries no token range. These are the proposal's `NodeKind` closed list; **the final `NodeKind` list is a T05/T01 co-freeze item**, and no kind beyond the proposal list is introduced.

2. **`NodeRecord` fields (candidate, per proposal §5/§6.1 `NodeDraft`).** `kind: NodeKind`, `first_token: Option<TokenId>`, `last_token: Option<TokenId>`, `parent: Option<NodeId>`, `ordinal: u32`. The root (`TranslationUnit`) has `parent: None`; every other node has `parent: Some(p)`; child ordinals under a committed parent are contiguous `0..n-1`.

3. **First/last committed `TokenId` ranges.** A node's range is **committed `TokenId`s only** (no `TokenDraft` and no same-batch token in M1; T05 writes **no** `sources.spans`). A leaf (`Identifier`, `IntegerConstant`) has `first == last`; a non-leaf has `first <= last` in committed token order; both endpoints must be committed tokens of the task's declared source. `ErrorRecovery` alone may be `None`/`None`. The verifiable checks are the existing proposal tests `node_token_range`, `node_token_range_committed_source`, `node_leaf_token_eq`; the stronger committed-token→PP-span provenance check is a T04/T05 co-freeze blocker and is **not** claimed here. For `2+3` the `BinaryExpression` range spans `2`..`3`; `Identifier`/`IntegerConstant` leaves are single committed tokens.

4. **Task request/result path.** Unified `ParseRequest(production, token_cursor, scope_id, context, binding_power)` → `ParseResult(node/declarator, next_cursor)` (the package's existing unified shape). All nesting goes through child tasks/continuations; `Payload` stays `RecordRef`-only. **OPEN (OB-30):** the closed `ResultValue` set has no scalar/tuple carrier for `next_cursor`; whether it is a new `ResultValue` variant, a record, or `ContinuationDraft.cursor` is a T05/T01 co-freeze item. Completion of the registered `parse.TranslationUnit` task uses the **item F** carrier candidate: committed `TaskState::Completed(ResultId)` whose `ResultId` carries the existing generic `ResultValue::Record(RecordRef::Node(root_node_id))` (the committed `TranslationUnit` `NodeId`), with **no** new typed result variant/family and **no** task-kind-only derivation. The request/result payload **variant spellings, `TaskKind` identity/registration, result typing, and encodings remain T05/T01 co-freeze** (items E/F).

5. **Continuation `ParseContext`/production mapping for the M1 grammar (candidate).** `context` is the grammar-category/entry constraint at the saved cursor; `production: TaskKind` is the registered parser task to resume; the two stay **distinct** (item E) and are **not** elided. A candidate context→M1 grammar-entry mapping, keyed by the **existing PA chip roles** of this package (no new task IDs invented), is: `TranslationUnit` → PA01 external-loop; `ExternalDecl` → PA02; `Specifier` → PA03; `Declarator` → PA05/PA06/PA07 (direct/pointer parts); `ParameterList` → PA09; `Block` → PA28; `Expression`/`Assignment`/`Unary`/`Primary` → PA22/PA24/PA20/PA16 (precedence-climbing entries; intended pairing Primary→PA16, Unary→PA20, Expression→PA22, Assignment→PA24, where `Expression`/`Assignment` may use `binding_power`). **Candidate-defect note (OB-30):** the pairing direction is stated here to remove an earlier ambiguous ordering; it remains a candidate, not a frozen mapping. The **exact parser-task→`context` one-to-one mapping, each member's exercise, `production: TaskKind` registration, and all discriminants/encoding/unknown-tag errors remain T05/T01 co-freeze**; the table above is the candidate, not a frozen mapping.

6. **Child enqueue ordering and await-all joins.** Per items A/B/C and proposal §5: a parse task that cannot finish in one tick appends its own `ContinuationDraft` (`previous` = its committed predecessor or `None`), `Enqueue`s the successor with `ContinuationRef::OwnBatch` (same-task only), and either `AwaitChildren { task, children: Vec<ChildRef> }` or `Progress`/`Complete`. Children resolve `OwnBatch` → committed child `TaskId`s in the same commit; the awaited set lives **only** in `TaskState::Waiting(WaitSet { children, host_request })` (no continuation `awaited`). On resume the parent decision is **await-all**: only after **all** committed children are terminal — all `Completed` → parent back to `Ready`; **any** `Failed` → parent `Failed` exactly once, never `Ready` — and the resumed parent is reinserted into `stage_queues[stage_of(parent.kind)]` (the parent **kind**, not `stage_of(continuation.production)`), handling an absent `continuation`. Ordering follows the frozen `(phase priority, enqueue ordinal, TaskId)` rule; a newly enqueued task is executable next tick (no same-tick re-entry). The `OwnBatch` pre-apply validation (phases/whole-batch `CommitError` before mutation; the exact phase label is an open co-freeze item — see OB-28) is item C, unchanged.

7. **Diagnostic vs invalid-ref distinction (candidate).** Semantic/recoverable parse faults are **chip diagnostics** emitted through `Fail`/`DiagnosticDraft` (e.g. `ParseCursorDidNotAdvance`, `ParseDepthExceeded`) and do **not** reject a batch; structural continuation/child-reference violations are **commit validation errors** (`ContinuationRefInvalid` / `AwaitChildrenRefInvalid`) that reject the **whole batch pre-mutation** (item C). Parse depth reuses `limits.max_task_depth` (parser continuation/child frames only), detected **before any child enqueue for the descent** (item D).
