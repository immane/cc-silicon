# T08: Constant, Layout, Initialization, and Dynamic Object Chips

Prerequisite T01; read T06 types, T07 checked facts or constant contexts to be checked. Directories `chips/constants/`, `chips/layout/`, `chips/initializers/`. Write constants/layout/init stores and proposals, do not read the host ABI. Semantic constant restrictions and optimization fold are strictly distinguished.

`ConstantRequest::Literal { literal: RecordRef::Literal, node, required_kind }` / `ConstantRequest::Binary { node, op, lhs: RecordRef::Literal, rhs: RecordRef::Literal, required_kind }` → `ConstantResult { value: RecordRef::Const, legality }` (the M1 variant set is **frozen by the OPEN-03 T01/T07/T08 co-freeze**, proposal rev 40; the operative shape is aligned with the selected H1 allocation, [CDR](CONTRACT_CHANGE_REQUEST_M1_PIPELINE_AND_PART_A_SCHEMA.md) rev 50 / proposal rev 36; the exact request/result payload variant spellings, reference encoding, task typing, and numeric codes remain `/6` T01/T07/T08 co-freeze — see the amendments below); `LayoutRequest(type, target, pack)` → `LayoutId`; `InitRequest(type, init_tree, storage)` → `InitPlan`. A symbolic address is not equal to a host pointer. VLA size and cleanup are left to the runtime plan and must not be passed off as static constants.

## M1-only constant evaluator candidate — integer literals `2`/`3` and folded `2+3`

It is not an owner/T08 or T01 `[INT]` sign-off, not a `/6` freeze, and authorizes no code.** It refines only the *meaning* of the already-accepted operative H1 request/result shape; it changes **no** field order, type, count, numeric code, or record family, and reinterprets **no** accepted text.

**Accepted semantics this candidate operationalizes (already selected; restated, not re-decided):**

- **Request consumed.** The sem-stage per-use `const.evaluate` request is the **frozen M1 variant set** (OPEN-03 co-freeze, proposal rev 40; T07 rev 4): `ConstantRequest::Literal { literal: RecordRef::Literal, node, required_kind }` for the leaf case and `ConstantRequest::Binary { node, op: ConstExprOp, lhs: RecordRef::Literal, rhs: RecordRef::Literal, required_kind }` for the binary case. T04 has **committed** the `LiteralRecord`(s) in `lex.literals`, and each variant **references** them via `RecordRef::Literal` (the literal is **not** re-embedded); `node` is a committed `NodeId`; `op` is T07's checked operator (`Add` in M1, **not** re-derived by T08); `required_kind` is the M1 `RequiredKind::IntegerConstantExpression`.
- **Lexical facts consumed, not re-derived.** T08 consumes the committed `LiteralRecord` fields already selected in CDR rev 45 — `kind` (`Integer`), `radix` (`10`), `suffix` (`None`), `value` (big-endian magnitude), `negative`, and `candidate_type` (symbolic `Int`, **no bit width**) — and does **not** re-tokenize, re-radix, or re-derive the candidate type.
- **Result produced.** The `ConstantResult` payload carries a **committed `RecordRef::Const`** result reference (the value lives in the T08-owned `ConstRecord`; T08 is the **sole** `constants.records` writer) **plus** `legality` with the M1 `ConstLegality` values `Legal`/`NotConstantExpression`/`Unsupported` and **no** separate legality record family.

**Candidate evaluator behavior (M1-only, bounded):**

1. **Lexical legality gate.** `required_kind == IntegerConstantExpression` and the referenced literal is `kind = Integer`, `radix = 10`, `suffix = None`. A referenced literal outside that exercised subset is `ConstLegality::Unsupported` (explicit, never a silent `Int` success) — consistent with the T04 no-silent-`Int`-default rule. A request whose `required_kind` is not `IntegerConstantExpression` is `ConstLegality::NotConstantExpression` (no M1 non-ICE `RequiredKind` variant exists yet).
2. **Integer literals `2` and `3` (leaf case).** Decode the committed big-endian `value` magnitude at decimal radix; apply the committed `negative` sign. For the M1 fixtures the magnitude is `2` or `3`, `negative = false`, so the mathematical value is `+2` or `+3`.
3. **Folded `2+3` (binary case).** The binary inputs arrive through the frozen `ConstantRequest::Binary { node, op, lhs, rhs, required_kind }` variant (OPEN-03 co-freeze, proposal rev 40): the two operands are the committed T04 `LiteralRecord`s `2` and `3` (source-order `lhs`/`rhs`), `op` is T07's checked `ConstExprOp::Add`, and `node` is the committed `BinaryExpression` use node. The candidate decodes both committed literals, evaluates the additive `+` on their mathematical integer values, and produces the folded result `5`; it does **not** re-parse the AST, re-lex the operator, or accept a hand-built value. This candidate **does not decide** C signed-overflow, wrap, or conversion behavior: it only fixes that the exercised `2 + 3` result is the mathematical `5` (representable under a sufficient M1 budget, no overflow path triggered).
4. **Result value and type (symbolic, target-independent).** The committed `ConstRecord` carries `ty` = the symbolic M1 integer type `int` with **no target bit width** (Part A symbolic; matches `M1-CL-03` and the accepted no-bit-width `Lx08CandidateType` selection) and `value` = the signed mathematical representative (`+5` for the folded case; `+2`/`+3` for the leaf cases). The unsigned interpretation is **type-level only** (`ty`); there is **no second stored value** (CDR §G Request G3 as a draft, restated here as candidate only). This committed-success path presumes the sufficient budget of point 5; under an **insufficient budget** the exercised evaluation yields the typed overflow/capacity result instead of a committed `ConstRecord`.
5. **`max_const_bits` origin/bound context (accepted source/projection/bound).** The zero-field T08 chip does **not** read `Limits`; the M1 cap comes from the accepted **explicit task-input projection** (origin = hashed `Limits` value `limits.max_const_bits`; M1 cap/default `128`; `config` rejects values `> 128`). The candidate's sole `max_const_bits` claim is that the exercised M1 results (`2`, `3`, `5`) are **representable under a sufficient budget** (e.g. the default `128`) — no overflow path is triggered for the exercised values at a sufficient budget. This is **not** a claim that every accepted valid `max_const_bits` value (any selected cap `<= 128`) suffices: at an **insufficient budget** (for example `1`, which cannot represent even the magnitude `2`) the exercised evaluation must produce a **typed overflow/capacity result** — the accepted `ConstOverflow` chip-diagnostic classification, whose exact trigger formula remains open — **not** a `Legal` success or a committed `ConstRecord`. The config minimum is **not** raised; budget sufficiency is an M1 success-acceptance condition, not a new config bound. This candidate does **not** settle the general overflow bound formula, the signed/unsigned representation, the representation carrier, or whether enforcement lives in the chip versus the commit; those remain open as stated below (and the CDR §G2 formula is at most an **unselected draft proposal/reference**, not a chosen rule). Where a bound is applied, an out-of-bound value is `ConstOverflow` (a **chip diagnostic** via the `Fail`/`DiagnosticDraft` path, **not** a `CommitError` variant; the commit does not recompute constant values) — the `ConstOverflow` classification is accepted, while its exact trigger formula and enforcement site remain open.
6. **Legality of the exercised results.** Under a sufficient budget (point 5), the M1 leaf and folded cases are `ConstLegality::Legal`, yielding a committed `ConstRecord` via `RecordRef::Const`; an insufficient budget yields the typed overflow/capacity result instead. Downstream (T09) consumes the committed fact; T09 owns IR `Constant` emission and does not recompute the value.

- **Representation type and carrier (`i128` vs `BigInt`; `ConstRecord` field set).** The `ConstRecord { ty, value: i128 }` carrier is the CDR §G **draft**, not a frozen shape and not a chosen rule; whether `value` is `i128` or an arbitrary-precision `BigInt`-style representation, and the exact `ConstRecord` field set/encoding, remain **open**. This candidate asserts only that M1 values are signed mathematical representatives that fit the bounded representation.
- **Error/diagnostic numeric codes.** `ConstOverflow`/`ConstUnsupported` are chip diagnostics (classification fixed), but the **exact numeric diagnostic codes**, the `RequiredKind`/`ConstLegality` numeric encodings, the `max_const_bits` wire field name, and the diagnostic code/hash encoding remain **open** `/6` T01/T08 co-freeze items.
- **Binary-expression inputs and committed links — RESOLVED by the OPEN-03 T01/T07/T08 co-freeze (2026-10-05; proposal rev 40).** The folded `2+3` input path is frozen: T07 emits `ConstantRequest::Binary { node, op: ConstExprOp, lhs, rhs, required_kind }` with the committed `BinaryExpression` `NodeId`, T07's checked additive operator (`Add` in M1), and the committed T04 `LiteralRecord` refs of the operands in source order; T08 decodes both committed literals, applies the checked additive fold, and commits **exactly one** `ConstRecord` for `5` (no per-operand `ConstRecord`, no join, no re-parse/re-lex, no hand-built value). T09 consumes the same committed `RecordRef::Const` (`ConstId`) and does not re-fold. The exact payload-variant spellings and every `RecordRef`/`RecordLink` tag encoding remain **open** `/6` hash-inventory items; the input-path shape is **not** open and must not be re-decided per implementation.
- **Broader C constant semantics.** Non-decimal radix, non-`None` suffix, character/string literals, unary/binary operators beyond additive `+`, casts, address/static-assert constants, and the `CL01`/`CL02`/`CL04`–`CL26` chips (incl. `CL03`'s probe-gated bit-pattern assertion `M1-CL-02`) are **out of this candidate's scope** and remain governed by their own acceptance and `/6` co-freeze; this candidate decides **no** behavior for them.
